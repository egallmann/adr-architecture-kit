# ADR-L-0004: ADR-to-Code Traceability via Decorators

**Status:** proposed  
**Created:** 2026-03-08  
**Modified:** 2026-03-08  **Authors:** adr-architecture-kit  
**Domains:** architecture, traceability, governance, verification  
**Tags:** traceability, decorators, verification, drift-detection, embodied-design  

**Related ADRs:** ADR-L-0001, ADR-L-0002, ADR-L-0003



---

## Context

Architecture Decision Records document WHY code exists, but there's no
machine-verifiable link from implementation back to the ADRs that justify it.
This ADR defines the foundation for a multi-tier governance architecture.

## Current State

- ADRs reference implementation via `implementation_identifiers`
- Code has no reverse link to ADRs
- No automated verification that code implements declared ADRs
- Manual effort to trace code changes to architectural decisions
- Drift detection is reactive, not proactive

## The STE Governance Vision

```
Project/Service
    ↓ defines
ADRs (Architecture Decisions)
    ↓ parsed by
Rules & Signal Service
    ↓ generates
Enforcement Rules + Signals
    ↓ activated by
Rule Library (MCP Service)
    ↓ projected to
Other Projects (consumers)
    ↓ enforced via
Decorators + Verification
```

This creates a **policy propagation system** where architectural decisions
in one project become enforceable rules in dependent projects.

## Multi-Tier Architecture

**Tier 1: Project Authority (This Project)**
- Projects define ADRs documenting their architecture
- ADRs contain invariants, capabilities, components
- Code annotated with decorators linking to ADRs

**Tier 2: Rules & Signal Service (Future)**
- Parses ADRs from projects
- Generates enforcement rules from invariants
- Generates signals for capability implementation
- Publishes rules to rule-library

**Tier 3: Rule Library (Sub-Module)**
- Activates rules from Rules & Signal Service
- Projects rules as MCP service
- Provides rule evaluation logic
- Enables cross-project rule consumption

**Tier 4: Verification & Enforcement (This Project + Consumers)**
- Decorator-based code annotation
- Bidirectional traceability verification
- CI/CD enforcement
- AI agent compliance checking

## Problems Solved

1. **Orphaned code**: Code exists with no architectural justification
2. **Incomplete implementation**: ADRs declare components that aren't implemented
3. **Drift**: Code evolves without updating ADRs
4. **Policy propagation**: Architectural decisions can't be shared/enforced
5. **AI reasoning**: AI agents can't trace code to architectural authority
6. **Cross-project governance**: No way to enforce architectural standards across services

## STE Principles

- **PRIME-1**: No implicit assumptions (code must declare its authority)
- **SYS-4**: Drift prevention (detect when code diverges from ADRs)
- **SYS-5**: Documentation-state as authoritative (ADRs govern code)
- **SYS-6**: RECON completion (architecture must be extractable)
- **Policy Propagation**: Architectural decisions become enforceable across projects


## Capabilities

### CAP-0001: Decorator-Based Code Annotation

Python decorators that annotate code with ADR references, creating

### CAP-0002: Bidirectional Traceability Verification

Automated verification that code matches ADR declarations in both

## Invariants

### INV-0027

**Statement:** All public classes and functions SHOULD be annotated with @implements_adr
decorator referencing the ADR(s) that justify their existence
  
**Scope:** global  
**Enforcement:** should (design)  
**Verification:** automated

**Rationale:**
Public APIs are architectural boundaries. They must have explicit
architectural justification. Private/internal code may omit decorators
if covered by class-level decorator.




### INV-0028

**Statement:** Decorator references MUST point to existing, accepted ADRs
  
**Scope:** global  
**Enforcement:** must (design)  
**Verification:** automated

**Rationale:**
Code cannot claim to implement non-existent or rejected ADRs.
This prevents invalid traceability claims.




### INV-0029

**Statement:** ADRs that declare components with implementation_identifiers MUST have
corresponding code with matching decorators
  
**Scope:** global  
**Enforcement:** must (design)  
**Verification:** automated

**Rationale:**
Forward traceability - if ADR declares implementation, it must exist.
Detects phantom declarations.




### INV-0030

**Statement:** Code decorated with @enforces_invariant MUST implement validation logic
for that invariant
  
**Scope:** global  
**Enforcement:** must (design)  
**Verification:** automated

**Rationale:**
Claiming to enforce an invariant without actually implementing the
enforcement is architectural drift.




### INV-0031

**Statement:** Traceability rules MUST be encoded in rule-library sub-module, not
hardcoded in validators
  
**Scope:** global  
**Enforcement:** must (design)  
**Verification:** automated

**Rationale:**
Rules are architectural artifacts that should be versioned, governed,
and reusable across projects.




### INV-0032

**Statement:** Rule library SHOULD support both file-based and MCP-based rule delivery
  
**Scope:** global  
**Enforcement:** should (design)  
**Verification:** automated

**Rationale:**
File-based for simplicity, MCP-based for dynamic rule serving to AI
agents and cross-project rule sharing.






## Decisions

### DEC-0001: Adopt Decorator-Based ADR Traceability

**Rationale:**
Python decorators provide a non-invasive way to annotate code with
architectural metadata without affecting runtime behavior.

Benefits:
1. **Machine-readable**: Decorators are parseable by AST analysis
2. **Non-invasive**: Don't affect code execution
3. **Composable**: Multiple decorators can be stacked
4. **Pythonic**: Idiomatic Python pattern
5. **Extractable**: RECON can extract decorator metadata

This enables:
- Automated verification of ADR implementation
- Detection of orphaned code (no ADR justification)
- Detection of incomplete ADRs (declared but not implemented)
- Traceability for audit and compliance
- AI agent understanding of code authority



**Consequences:**

**Positive:**
- All new code must declare its ADR authority via decorators
- RECON must extract decorator metadata
- Verification tools must validate decorator references
- Existing code needs gradual annotation
- Decorator library becomes foundational dependency



### DEC-0002: Create Rule Library Sub-Module as MCP Service

**Rationale:**
ADR traceability rules should be encoded in a separate rule-library
sub-module that acts as an MCP service, not hardcoded in validators.

## Multi-Tier Governance Architecture

**Projects** define ADRs with invariants and capabilities
    ↓
**Rules & Signal Service** parses ADRs and generates enforcement rules
    ↓
**Rule Library** (this sub-module) activates and projects rules via MCP
    ↓
**Consumer Projects** receive rules and enforce via decorators/verification

This enables:
1. **Policy Propagation**: ADRs in one project become rules in others
2. **Centralized Governance**: Rules & Signal Service is authoritative
3. **Distributed Enforcement**: Each project enforces via rule-library
4. **Dynamic Rules**: Rules update when ADRs change
5. **Cross-Project Standards**: Shared architectural standards

The rule-library sub-module will:
- Receive rules from Rules & Signal Service (or load from files)
- Activate rules for specific projects/contexts
- Project rules via MCP to AI agents and tools
- Provide rule evaluation logic
- Support file-based fallback (for development)

## Rule Flow

```
adr-architecture-kit/adrs/
    ↓ (parsed by Rules & Signal Service)
Generated Rules:
  - "Public classes must have @implements_adr"
  - "Code must enforce declared invariants"
    ↓ (published to rule-library)
rule-library/ (MCP Service)
    ↓ (consumed via MCP)
Consumer Projects (ste-runtime, other services)
    ↓ (enforced via)
Decorators + Verification
```



**Consequences:**

**Positive:**
- New sub-module: rule-library/ (MCP service)
- Rules generated from ADRs, not manually written
- MCP protocol for rule delivery
- File-based fallback for offline/development
- Rules versioned and governed
- Cross-project rule consumption
- AI agents receive rules via MCP



### DEC-0003: Support Bidirectional Verification

**Rationale:**
Traceability must work in both directions:

**Forward (ADR → Code)**:
- ADR declares component with implementation_identifiers
- Verify that code exists and has correct decorators

**Reverse (Code → ADR)**:
- Code has @implements_adr decorator
- Verify that referenced ADR exists and is accepted

This bidirectional verification detects:
- Orphaned code (no ADR)
- Phantom declarations (ADR but no code)
- Invalid references (code references non-existent ADR)
- Status mismatches (code implements "rejected" ADR)



**Consequences:**

**Positive:**
- Verification must check both directions
- RECON must extract both ADR declarations and code decorators
- Drift detection becomes comprehensive
- CI/CD can enforce traceability
