# ADR-L-0016: Deterministic Corpus Query and Authoring Orientation APIs

**Status:** accepted  
**Created:** 2026-04-14  
**Authors:** adr-architecture-kit  
**Domains:** repository, discovery, authoring  
**Tags:** repository-api, corpus-query, authoring-orientation  

**Related ADRs:** ADR-L-0013, ADR-L-0017



---

## Context

Upstream authoring workflows need deterministic ways to inspect the compiled
corpus, orient themselves within a scope, and allocate new ADR identifiers
without reparsing registry YAML or hand-implementing directory scans.

The existing ArchitectureRepository already exposes typed entity and
relationship access, but it does not yet provide one compact orientation
summary, first-class manifest/index accessors, or a supported next-ID helper
for forward authoring workflows.


## Capabilities

### CAP-0045: Deterministic Corpus Orientation Surface

Provide one supported API and CLI surface for manifest access, index
access, corpus summaries, relationship inspection, and scope-local next
ADR ID allocation.






## Invariants

### INV-0069

**Statement:** Forward-authoring ADR ID allocation MUST be monotonic and non-reusable.
Previously allocated IDs and historical gaps remain consumed history and
MUST NOT be reissued.
  
**Scope:** global  
**Enforcement:** must (design)  
**Verification:** automated

**Rationale:**
Reusing ADR identities corrupts provenance, historical references, and
deterministic traceability.




### INV-0071

**Statement:** Reserved ADR IDs `9000-9999` MUST NOT participate in standard forward
authoring allocation.
  
**Scope:** global  
**Enforcement:** must (design)  
**Verification:** automated

**Rationale:**
Exceptional identities need a governed range that does not distort the
normal forward allocation sequence.






## Decisions

### DEC-0069: Extend ArchitectureRepository with deterministic orientation helpers

**Rationale:**
Repository consumers should use one in-process boundary for manifest
access, architecture index access, corpus summary generation, entity
reference lookup, and forward-authoring ID allocation.



**Consequences:**

**Positive:**
- Upstream tools stop duplicating manifest and index loading logic
- Corpus orientation becomes one stable typed API instead of ad hoc YAML reads
- Next-ID allocation stays scope-aware, deterministic, and monotonic



### DEC-0070: Expose corpus summary and relationships through supported CLI commands

**Rationale:**
Human and script consumers need stable CLI ergonomics that mirror the
repository boundary without treating raw registry files as the user-facing
interface.



**Consequences:**

**Positive:**
- `adr entities summary` provides one deterministic orientation surface
- `adr entities relationships` exposes graph-level inspection without custom parsing
- CLI and Python APIs stay aligned around the same repository boundary



### DEC-0073: Make forward-authoring ADR ID allocation monotonic and non-reusable

**Rationale:**
ADR identifiers are architectural identity, not recyclable sequence
numbers. Once an ID is allocated, gaps must remain consumed history even
if an ADR is later deleted, superseded, or removed from the active corpus.



**Consequences:**

**Positive:**
- Historical traceability is preserved
- Allocation remains deterministic without gap filling
- Deleted artifacts cannot silently reactivate old identities



### DEC-0075: Exclude reserved ADR IDs 9000-9999 from standard forward allocation

**Rationale:**
Brownfield onboarding and imported architectural records need a controlled
exceptional range where identity can be preserved without perturbing the
normal authoring sequence.



**Consequences:**

**Positive:**
- Standard allocation remains predictable below 9000
- Brownfield or imported records have a governed preserved-identity range
- Reserved-range artifacts do not pollute the normal forward sequence
