# ADR Kit v1.1 Integration Guide

## Overview

ADR Kit v1.1 now treats the generated architecture-index bundle under `adrs/index/` as the primary discovery surface for agents and tooling. Canonical authority remains in ADRs and standalone invariants. Legacy `adrs/entities/registry.yaml` remains available as a compatibility projection.

## Discovery Surfaces

### Architecture Index Bundle

**Location**: `<scope-root>/adrs/index/`

**Bootstrap file**: `<scope-root>/adrs/index/architecture-index.yaml`

**Contents**:
- `architecture-index.yaml`
- `entity-registry.yaml`
- `relationship-registry.yaml`
- `unresolved-registry.yaml`
- `decision-registry.yaml`
- `capability-registry.yaml`
- `invariant-registry.yaml`
- `component-registry.yaml`
- `system-registry.yaml`

### Normalized Entity Registry

**Location**: `<scope-root>/adrs/index/entity-registry.yaml`

Purpose:
- normalized exact-ID lookup
- deterministic ingestion
- graph-lite bootstrap before RECON composition

Example:

```yaml
schema_version: "1.1"
type: normalized_entity_registry

entities:
  - id: CAP-0015
    entity_type: capability
    name: AI Request Routing
    summary: Route AI requests to the correct provider
    canonical_source:
      source_type: logical_adr
      source_ref: ADR-L-0007#CAP-0015
      artifact_path: adrs/logical/ADR-L-0007-ai-gateway-architecture.yaml
```

### Relationship Registry

**Location**: `<scope-root>/adrs/index/relationship-registry.yaml`

Purpose:
- first-class edge records
- provenance-aware graph ingestion
- minimal interpretation at load time

### Unresolved Registry

**Location**: `<scope-root>/adrs/index/unresolved-registry.yaml`

Purpose:
- preserve architecture gaps as visible signals
- distinguish real, deferred, and resolved source-state intent
- surface generator-derived reference problems

Gap semantics:
- `author_declared_real_gap`
- `author_declared_deferred_gap`
- `author_declared_resolved_gap`
- generator-derived unresolved types such as missing references or malformed links

## Workflow

### Compilation Pipeline

```text
canonical ADRs + standalone invariants
    -> source discovery
    -> raw extraction
    -> ID-based normalization
    -> canonical source assignment
    -> relationship derivation
    -> unresolved surfacing
    -> adrs/index/*
```

### Typical Commands

```bash
adr normalize-canonical-ids --scope .
adr generate-architecture-index --scope .
adr generate-manifest --scope .
adr generate-rendered-docs --scope .
adr generate-system-overview
```

## Validation

Architecture-index generation remains strict:
- duplicate canonical entity IDs fail
- unresolved registry IDs must be unique per scope
- relationship endpoints must resolve to known entities
- generated outputs must be deterministic

Legacy compatibility:
- `adrs/entities/registry.yaml` is regenerated from the normalized pipeline
- `adr generate-entity-registry` is a compatibility wrapper over `adr generate-architecture-index`
- `adrs/manifest.yaml` remains a summary-oriented derived surface

## RECON Contract

RECON should load discovery in this order:
1. `architecture-index.yaml`
2. `entity-registry.yaml`
3. `relationship-registry.yaml`
4. optional `unresolved-registry.yaml`
5. optional canonical artifacts

Repo-local registries keep local IDs only. Global uniqueness is added later by namespace composition, for example `adr-architecture-kit::DEC-0009`.

## Best Practices

1. Regenerate `adrs/index/*` after changing ADRs or invariants.
2. Treat `adrs/index/` as generated-only.
3. Use unresolved entries as architecture signals, not as hidden warnings.
4. Keep legacy registry consumers on `adrs/entities/registry.yaml` only until they can switch to the architecture index bundle.
