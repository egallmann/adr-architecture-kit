# ADR-V-0012: Code Decorators (Intent Primitive)

**Status:** proposed  
**Created:** 2024-03-10  
**Authors:** adr-architecture-kit  
**Domains:**   
**Tags:** code-decorators, intent, traceability, semantic-graph  




---

## Context

Code lacks explicit architectural intent:
- Functions exist but don't explain why
- Classes exist but don't link to design
- Modules exist but don't reference ADRs

Problems:
- Intent is implicit (must infer from code)
- Traceability is manual (search for related ADRs)
- Validation is impossible (can't verify code matches ADR)
- Review is broad (can't isolate relevant code)

Example:
```python
def authenticate_user(token: str) -> User:
    # Why does this exist?
    # Which ADR defines this?
    # What invariants must it maintain?
    # Unknown.
```

Opportunity: Explicit intent markers in code.

## The Slice Architecture Insight

RECON extracts code into slices (AST-based semantic entities):
- Function slices (function definitions, signatures, dependencies)
- Class slices (class definitions, methods, relationships)
- Module slices (imports, exports, structure)

ADRs are also extracted into slices:
- ADR metadata slices (id, title, status, tags)
- Component specification slices (interfaces, requirements)
- Relationship slices (implements, references, supersedes)

**Problem**: How do we link ADR slices to code slices?

**Solution**: Code decorators are explicit edges in the semantic graph.

```
ADR Slice (ADR-PC-0042)
      ↓
  [edge: implements]
      ↓
Code Slice (authenticate_user function)
```

Just like AST code slices have edges (function calls, imports),
ADR-to-code relationships need explicit edges (decorators).

**This is how the decorator idea emerged**: We needed explicit, extractable
edges to build a bidirectional graph between architecture (ADRs) and
implementation (code).
